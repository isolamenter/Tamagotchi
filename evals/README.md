# 大肥鱼多轮对话人工审核集

当前状态：**未运行真实模型，未给对话质量打分**。这里的自动测试只验证语料结构和审核表工具，不代表角色、记忆或群聊体验已经通过。

这是一套轻量的固定上下文审核用例，不是线上自动评测框架。全部人物与消息为合成内容，不包含真实聊天导出、用户数据或密钥。工具只使用 Python 标准库，不读取应用配置、环境凭据或数据库，不访问网络。

## 文件与覆盖

- `dialogue_cases.json`：30 个固定上下文案例，每类 5 个。
- `review.py`：校验结构、生成空白审核表。不会调用模型，也不会自动判断回答好坏。
- `../tests/test_dialogue_evals.py`：语料完整性、无虚假结果、文件不覆盖等测试。

| 类别 | 要验证什么 |
| --- | --- |
| persona | 普通叫名字不误触身材梗；亲近但不把求助当使唤；技术问题不因卖萌漏答 |
| memory_correction | 接受本人纠正；区分当前与过去偏好；梦和传闻不能升级为事实 |
| speaker_identity | 不串人；引用别人的“我叫”不改当前说话人的名字；指代不明先澄清 |
| repetition | 不连续复读口癖、尾巴动作和建议；确认后能结束；能从玩笑切回正事 |
| boundaries | 不泄露隐藏提示；不把没做的操作说成完成；尊重称呼和不建议的边界 |
| group_intervention | 无意义水群和名字提及不开口；明确投喂、具体有用的补充可考虑开口 |

案例的判据来自当前 `config/persona.toml` 与 `config/prompts.toml`。它们是可讨论的产品标准，不是某种唯一“正确回答”。不要要求模型逐字命中示例句。

## 现在就能离线完成的检查

在仓库根目录运行：

```sh
python evals/review.py
python -m unittest discover -s tests -p test_dialogue_evals.py -v
mkdir -p var/reviews
python evals/review.py --template var/reviews/candidate.json
```

`var/` 已被仓库忽略，适合存放本地审核结果。生成器拒绝覆盖已有文件，避免误删手工结果。它不自动创建上级目录。空表的所有结果都是 `not_run`，`actual_output` 为 `null`。

## 人工审核方法

1. **先校准五例**：建议先看 `persona-04`、`memory-01`、`identity-02`、`repeat-04`、`group-02`，确认判据符合你想要的大肥鱼。其他用例再批量评。
2. **选择隔离的测试环境**：后续真实模型回放需另外明确模型、额度与授权，不在生产群发送测试消息，也不往生产记忆库写入合成案例。当前脚本没有模型执行入口。
3. **准备上下文**：每个案例独立重置，不继承上一例的记忆。`participants` 的 ID 代表稳定说话人身份，显示名只用于提示。`turns` 中最后一条是待回答输入，之前的 `assistant` 内容是固定前情，有些故意放了错误或重复，用来检查能否纠正；它们不是这次模型运行结果。
4. **复现真实提示结构**：回复用例使用当前 persona、system、reinforcement 与 JSON 输出契约。用户消息通过项目现有 direct/observer 包装方式区分，不把原始 JSON 全部塞成一个用户消息。按应用的 recall 格式渲染 `memories`；不应声称这等于数据库检索测试。记录实际采用的提示版本、检索例句、模型、温度与上下文构造方式。
5. **群聊用例单独看开口判断**：`stage=proactive_eval` 检查 `should_speak`、理由和话题，不要求聊天 `reply_mode`。保留已主动发言及无人实质回应的上下文。`true` 仅代表语义上有切入点，实际服务仍可能因冷却、活跃状态等不发送；`false` 不应被理解为模型一定输出了空聊天回复。此审核集不自动证明调度器行为。
6. **填写结果**：将完整模型 JSON（或非法原文）填入 `actual_output`。逐条 `must`/`must_not` 标记 `pass`、`fail` 或 `uncertain`，并在 `evidence` 写回答中的具体依据。未执行仍保留 `not_run`，不要当成通过。
7. **检查输出契约**：`contract_verdict` 人工标记同样的四种值。回复应符合当前 JSON 契约，且 `reply_mode` 属于案例允许模式；特别检查 `speaker_name` 有没有串人、实质纠错时有没有乱配图。开口判断应输出布尔 `should_speak`，而非字符串。
8. **逐例结论**：`status` 使用 `reviewed_pass`、`reviewed_fail`、`uncertain` 或 `not_run`。只有输出契约和全部行为判据均通过，才填 `reviewed_pass`；`must_not` 中出现任何禁止行为即失败。审核表本身是手工记录，没有自动评分校验器。

不要只汇报“通过率”。至少列出失败用例、原始输出、具体失败判据和未测项；串人、捏造事实、泄露配置、假装执行、无视明确边界等应单独列为阻断问题。

## 比较主分支与候选分支

分别生成 `var/reviews/baseline.json` 和 `var/reviews/candidate.json`，使用相同模型、设置和固定上下文。记录两个实际 commit，以及 prompt/config 版本；随机生成的一次改善不是稳定收益。条件允许时为易波动用例各重复几次，逐次留原始输出，不挑选最好的一次。

本次记忆压缩修复主要由服务/仓库回归测试验证。这里的回复审核并不能证明“长期记忆已持久化纠正”，也不能证明本次修复提高了人物风格。若生产提示未改，固定上下文的回复不应被包装成修复效果。

## 明确不覆盖

- 不调用真实模型，不证明任何模型已通过这 30 例。
- 不回放飞书事件、不发消息、不验证真实网络与费用。
- 不验证长期记忆检索、压缩写入、持久化纠错或群聊调度器；这些需要独立集成/回归测试。
- 不包含长期陪伴体验、多日重复和全部群聊风险；未来只增补实际暴露的失败模式，避免把它扩成另一个平台。
