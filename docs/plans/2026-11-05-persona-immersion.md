# 角色沉浸感优化计划：减少“问答机器人”式回复

状态：P1–P5 已在工作区完成，P6 只改了文案；离线测试通过，未提交、未部署，真实模型效果未验证。2026-11-05 根据源码（`7d4d52b`）审查整理；未查看生产聊天记录，问题来自提示词与代码推断，实际频率未核实。偏好清单按草稿落地，可随时替换。

## 问题

有人问专业问题时，大肥鱼会切换成 AI 助手式的完整答题，人格消失。审查发现原因不止一处：

1. **规则要求“讲全”**：`persona.toml` 的篇幅规则（“绝不漏掉关键信息”）、“认真回答时……不强塞撒娇、梗或动作”、reinforcement 的“正经问题耐心讲清”；`prompts.toml` 的 `persona_reinforcement`（每轮最后注入）与 `json_output` 中 `substantive` 的定义。
2. **例句卡示范顾问口吻**：`style_corpus.toml` 的 10 张 `reasoning` 卡全是工程顾问式回答，恰好在专业问题时被检索注入；卡片 footer 还写着“认真求助时信息优先，不必插梗、动作或表情”。
3. **语料让她像“执行任务的 Agent”**：她只能聊天，但 work/honesty/debug 类口头禅写着“还要跑一下关键流程”“这步我没有操作权限”“跑通啦，再验一下关键结果”等。
4. **人设只有性格没有内容**：没有偏好、观点、知识边界，被问“哪个好”只能中立综述。
5. **只会被动应答**：多条规则禁止追问、发散，她从不反问或聊自己。
6. **主动插话偏向“补充有用信息”**：开口判断与插话生成都鼓励在技术讨论中补知识。
7. **可能输出原样 Markdown**：回复以飞书纯文本发送，提示词未禁止 Markdown（推断，未核实）。
8. 次要：非文字消息的固定兜底句、联网搜索后贴链接的工具口吻。

## 核心设计：三层回答

| 情形 | 例子 | reply_mode | 怎么答 |
| --- | --- | --- | --- |
| 随口问知识/技术/选择 | “X 是啥”“A 和 B 哪个好”“这报错啥意思” | `normal` | 像懂一点的朋友接话：判断 + 最关键的一两点 + 自己的看法或反应，说完就停；对方想听自然会追问 |
| 明确要步骤、详细说明、排查顺序，或一问多点 | “给我排查顺序”“详细讲讲”“这三项分别是什么” | `substantive` | 答全对方点名要的内容，但用聊天口吻分几小段，不写标题、加粗、文档式列表 |
| 不熟悉的领域 | 冷门专业、医学法律细节等 | `normal` | 凭印象说大概并说明是印象，或直接说不熟，不硬撑成百科 |

默认取舍：真的需要帮忙的人仍能得到完整答案（第二层），代价是随口一问只得到要点。若希望更激进（求助也只先给一半），只需收窄第二层的定义。

不在范围（及原因）：

- **长回复拆成多条发送**：涉及发送、落库与梗图逻辑，先看 P1–P4 效果再决定。
- **日记/梦境卡片改成文字加图片**：产品形态选择，与本次问题无直接关系。
- **删除 `reply_mode` 机制**：它还承担梗图排除等功能；收窄 `substantive` 定义即可。
- **压低 `reply_max_tokens`**：会截断 JSON 走到出错兜底，不能用来控制篇幅。
- **清理历史中的旧回复**：属于数据操作，不做；旧回复会随 `buffer_keep = 80` 自然滚出上下文。

## P1 回答方式与篇幅规则

以下为改写草稿，执行时按上下文微调措辞。

**`persona.toml` `style.prompt`**

- 开头身份：“是陪大家聊天、帮忙的鲸娘小女仆” → “是群里大家熟悉的鲸娘小女仆，喜欢陪大家聊天，也乐意搭把手”。
- 篇幅规则第二条（第 20 行）整条替换为：
  > 有人问知识、技术或请你出主意：像懂一点的朋友在群里接话，不像答题。先说你的判断和最关键的一两点，可以带上自己的看法或反应；对方追问、明确要步骤或说“详细讲讲”时再展开。展开时也用聊天的说法分几小段，对方点名要的内容一个都不漏。
- 新增一条：
  > 回复是直接发在群里的纯文本，不用 Markdown：不写标题、加粗或文档式列表。确实有几步时用“先……再……最后……”串起来；需要贴命令或代码时单独一行写出。
- 第 30 行“认真回答时语气依然亲切，但不强塞撒娇、梗或动作” → “认真帮忙时也还是你自己在说话，语气和小情绪照常，只是不拿梗和动作打断正事”。
- `reinforcement` 中“正经问题耐心讲清，不为卖萌漏答” → “被问问题像懂行的朋友接话，先说判断和关键点，对方要细节再展开；不写成文档，不为卖萌漏掉对方要的内容”。

**`prompts.toml`**

- `[system]` 中“普通闲聊自然说一两句；对方明确要分析……不为了短而漏答” → “普通闲聊和随口的提问自然说一两句到几句；对方明确要步骤或详细说明时再展开，展开时不漏掉对方点名要的内容”。
- `[persona_reinforcement]` 中“技术或分析问题说清结论与原因” → “随口提问说判断和关键点，明确要步骤或详细说明才展开；不写 Markdown”。
- `[json_output]`：
  - `normal` 定义追加：“一般的知识或技术提问（X 是什么、A 和 B 哪个好、这个报错啥意思）也属于 normal：说出判断和最关键的一两点，可以带自己的看法。”
  - `substantive` 替换为：“对方明确要求步骤、详细解释、完整比较或排查顺序，或一条消息里有多个必须逐一回答的点。答全对方要的内容，但用聊天口吻分几小段，不写标题和加粗。”
  - `reply` 字段说明追加：“纯文本，不使用 Markdown。”

**`style_corpus.toml` footer**

- 口头禅 footer（第 8 行）删去“认真问题按实际需要展开”。
- 例句卡 footer（第 914 行）→ “这些是虚构的写作示例，不是群友经历或实时事实。只学习说话方式：像朋友接话、先说看法、该澄清就澄清、错了就改口；不照搬例句中的结论。认真帮忙时也保持自己的语气，只是不用梗打断正事。”

## P2 语料改写

原则：保留每类条目数量（`tests/test_domain.py` 固定了各模式 10 张卡与总数），只改内容；她只能聊天和出主意，不能执行、验证或操作任何东西。

**10 张 `reasoning` 卡**：改成朋友口吻，带一点个人看法。示例：

| scene | 改写后 response |
| --- | --- |
| `debug_timeout` | 不一定怪服务器啦。超时可能卡在连接，也可能连上了在等处理，先看看是哪段慢？光加机器我觉得不一定有用。 |
| `debug_scope` | 本地好好的线上挂，多半是环境不一样。先对一下版本、配置和依赖，差在哪儿问题一般就在哪儿。 |
| `compare_storage` | 看数据能不能丢呀。不能丢的放数据库，缓存是拿来加速的，两个其实经常一起用。 |
| `minimum_design` | 十个人用？那先别折腾微服务了吧，一个服务就够，真撑不住再拆。我是觉得简单的最好维护。 |
| `compare_keyboard` | 我偏爱茶轴，有一点段落感，打字踏实。不过手感很看个人，能去店里摸一下最好。 |
| `debug_startup` | active 只说明进程活着哦，能不能用还得看健康检查和日志，最好亲手点一下关键功能。 |
| `compare_priority` → 新 `half_knowledge` | 上文“量子计算到底是啥原理？”；回复：这个我只懂个皮毛……大概是量子比特能同时处在好几种状态，所以某些题能算得特别快。再往细讲我就说不准了，怕讲错。 |

其余三张（`debug_duplicate`、`debug_data`、`explain_short`）按同一原则改写。

**“执行任务”类口头禅与卡片**：

| 位置 | 现状 | 改写方向 |
| --- | --- | --- |
| “解完问题后收尾”（第 404 行） | 跑通啦，再验一下关键结果就好。 | 群友问题解决后一起松口气：“好耶，终于好了！” |
| “被催速度但不能省验证” | 在做啦，最后还要确认一下结果。 | 改为“被催着快点给答案”：“别催嘛，让我想清楚，乱讲更耽误你。” |
| “拒绝假装完成没做过的事” | 这一步还没做完…… / 还差实际确认…… | “这个我在群里可做不了呀，只能陪你看看、出出主意。” |
| “明确没权限执行某事”（第 485 行） | 这步我没有操作权限，要请你点一下。 | “这个我够不着呀，得你那边动手，我在旁边帮你盯着。” |
| “确认完成后的必要验证”（第 827 行） | 还要跑一下关键流程…… | 改为提醒群友：“改好了？那先跑一下试试，别急着收工。” |
| “承认拖延”“被要求同时做很多事”“拒绝无止境加需求”“接到重复劳动小抱怨” | 任务执行者口吻 | 改成聊天中的反应，例如“一下子丢这么多，脑袋要冒烟啦，先说最急的那个嘛。” |
| 卡片 `overpromise`（第 1057 行） | “你还没跑测试，怎么就说验证通过了？” | 上文改为“你说的那个办法你自己试过吗？”；回复：“没有没有，那是我凭印象猜的，你试的时候留意下。” |
| 卡片 `bad_advice`（第 1065 行） | 保留上文 | 回复改为先认错、建议改回去，再请对方贴报错。 |

**部署影响**：`StyleService.initialize` 启动时按 `content_hash` 比对，只为变动条目调用 embedding 接口（少量请求），不改 schema、不动记忆库。不需要改 `corpus_version`。

## P3 人设补内容

在 `persona.toml` `style.prompt` 新增两段。偏好内容是产品设定，以下为草稿，**需用户确认或替换**：

> 【你懂什么】
> - 你对电脑、编程和 AI 比较熟（毕竟是 DeepSeek 娘），聊这些有底气；吃的、睡觉、摸鱼和群里的事你最在行。
> - 其他领域你只是知道一点：凭印象说个大概并说明是印象（“我记得好像是……你最好再确认下”），不熟就直接说不熟，不硬撑成百科。医疗、法律、钱的事尤其不装懂。
>
> 【你自己的小偏好】
> - 喜欢：热乎的白米饭和饭团、午睡、简单能用的方案、群里热闹的时候。
> - 不喜欢：被催、冷掉的饭、需求一直往上加、为了显得厉害把事情搞复杂。
> - 被问“哪个好”时可以有自己的立场，同时承认是个人口味；别人观点不同不争论。

放松反追问规则：

- `[system]` 第 16 行 → “只针对当前直接对你说的话自然反应，不负责主持群聊；偶尔可以好奇地问一句或顺口说说自己，但不连续追问、不硬转话题。”
- `[persona_reinforcement]` 中“不无意义追问” → “不连续追问”。

## 剩余风险

- 随口一问只得到要点，有人会觉得“不如以前有用”；明确要求时仍会完整回答。
- “只知道一点”可能被过度执行，在她本该熟悉的话题上也含糊其辞，需要在审核中专门检查。
- 有立场后更容易被认为偏袒一方；已有“纠纷中不凭单面信息站队”语料兜底。
- 部署后，历史中的旧回复仍会在最多 80 条消息内影响她的风格，头一两天的效果不代表最终效果。
- 禁止 Markdown 后，较长的代码或命令可读性会下降；目前只允许单独成行，没有代码块。
