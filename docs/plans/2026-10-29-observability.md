# VPS 日志与报错收集轻量实施方案

状态：待实施。2026-10-29 根据当前源码和 gcp-vps 只读检查修订。交付目标是后台能查到关键过程、具体错误原因及代码位置；不建设独立监控平台。

最近 24 小时 `tamagotchi` journal 元数据统计：2,969 条，JSON 导出约 3.29 MiB，其中 webhook access 1,308 条、模型诊断 299 条、reply generated 60 条、含 WARNING 文本 50 条、含 ERROR 文本 1 条、GM access 124 条、health access 11 条。分类按文本匹配，可能交叉，并不等于唯一请求/故障数；导出含 journal 元数据，不等于实际磁盘增量。本次 50,000 条读取上限未触及，未输出日志正文。

结论：容量充足到可以保留有用历史；内存更需要克制。采用轮转文件与后台按需查询，不引入第二个数据库、独立采集进程、日志搜索集群或新的付费服务。

## 2. 推荐资源范围

| 资源 | 建议范围 | 首次默认值与边界 |
| --- | --- | --- |
| 应用诊断文件总量 | 32–128 MiB | 默认 64 MiB，包含当前文件与全部轮转文件 |
| 错误/警告文件 | 16–64 MiB | 默认 32 MiB，8 MiB × 4 份，保护错误历史 |
| 关键正常事件文件 | 16–64 MiB | 默认 32 MiB，8 MiB × 4 份 |
| 单条日志 | 正常通常小于 2 KiB，异常上限 16 KiB | 先保留原因/上游码/代码位置，再裁剪长堆栈；标明截断 |
| 待写队列 | 不超过 128 条 | 入队前序列化且截断，负载上限约 2 MiB；不持有异常对象/请求/正文引用 |
| 新增内存 | 目标常驻增量不超过 10 MiB | 实测空闲、连续写入、查询及错误风暴；不是已验证指标 |
| 单次后台查询 | 默认 50、最多 100 条 | 分块反向读取；扫描字节上限 2 MiB，以游标继续，不将 64 MiB 全读入内存 |
| 查询并发 | 同时 1 个文件扫描 | 查询离开事件循环；过载时快速返回忙碌，不建立无界等待队列 |
| 系统 journal | 全机 256–512 MiB | 建议另行配置为 256 MiB，KeepFree 2 GB；应用与系统日志总预算约 320 MiB |

轮转按大小强制生效，磁盘满或权限失败不能导致聊天失败。磁盘预算可配置，但首次不开放无限保留。保留期以容量为准；普通事件希望覆盖约 7 天、错误约 14–30 天，实际天数上线后按新日志日增量计算，不能用 journal 导出体积直接保证。

journal 是全机共享的，收紧上限及 vacuum 会影响其他服务历史，必须作为独立运维变更明确授权，不能随应用部署顺手清理。本次未修改该设置；仅检查 `/etc` 配置未见所筛选的显式容量项，实施时还应核对发行版与其他目录的有效配置。

## 3. 轻量存储与接入方式

新增一个小型日志模块，复用 Python logging。文件使用逐行 JSON，分为 `errors.jsonl` 和 `activity.jsonl`：WARNING/ERROR 只写错误文件；明确选中的关键 INFO 只写活动文件，不在两份应用文件内重复保存。

保留现有 stdout/journal 诊断通道，保证应用页面不可用时仍可 SSH 排查。向两种输出发送前统一脱敏；不假定所有现有日志都已经安全。

应用内只增加一个写入线程和有界队列；不增加进程、数据库连接池、索引器、定时全盘扫描或后台全量统计。写入线程负责有限文件轮转，失败限频输出 stderr 并累计失败计数，禁止递归记日志。

队列为错误预留空间。拥塞优先舍弃正常事件；错误仍可能在持续风暴中丢失，必须显示丢弃计数。先在内存累计采集状态，下一次可写时保存丢弃摘要。正常关闭有限时间内排空队列，进程强杀不保证队尾无损。

目录放在发布目录外，例如 `/home/akiya/tamagotchi/logs/`，环境配置指定；目录仅服务用户可访问，日志文件权限 0600。日志不进入源码发布包、Git 或业务数据库备份；不复制历史发布的日志文件。

轮转总数包含当前文件，例如 backupCount=3 才是总计 4 份。单条大小在写入前限制，避免一个超大异常突破文件预算。查询只打开预定义日志文件，不接受客户端传入任意路径；轮转导致游标失效时明确提示刷新，不伪造空结果。

## 4. 所有主要错误都必须有原因

每条错误至少记录：时间、级别、模块/操作、异常类型、经过脱敏的具体原因、应用代码堆栈位置；有上游调用时记录 HTTP 状态、业务错误码和 request ID。有请求/会话/消息/后台任务上下文时一并关联。

原因内容包括异常链，不只记录最外层 RuntimeError。TimeoutError 本身为空时，补充具体操作、超时预算与已等待耗时。JSON 错误记录 msg、行列、位置、输出长度；不记录出错文档。上游失败优先提取安全的 error.message/code/status 与请求编号，不把完整 SDK exception body 直接写入。

| 场景 | 需要保留的原因和影响 |
| --- | --- |
| HTTP 未捕获异常 | 具体异常链、代码位置、路由模板、request/error ID；响应给同一编号，不返回内部堆栈 |
| 飞书回调处理 | JSON/解密/校验失败类别、message/event ID；BackgroundTasks 的处理失败单独捕获，HTTP 200 不算业务成功 |
| 直接回复生成 | provider/model、用途、超时/连接/限流/鉴权/截断/解析原因；兜底发送成功仍明确标为降级 |
| 飞书发送/上传/卡片更新 | HTTP 状态、业务码、安全错误摘要、平台请求编号和发送阶段；区分明确失败与超时结果未知 |
| 发送后本地落库 | 已获平台成功后业务库写失败单列，不误导成消息未发送 |
| 记忆/整理/向量/风格 | 失败阶段、会话/任务、具体原因、进度是否回滚或功能降级 |
| 主动发言/梦境/日记 | 语义判断异常、模型失败、生成图/上传失败、发送失败分别记录；正常不发言不是错误 |
| 图片识别/梗图/姓名查询/表情回应 | 即使最终继续主流程，也保留失败原因和降级影响 |
| asyncio | spawn、直接 create_task、事件循环未处理异常；正常取消不报错 |
| 启动/关闭 | 尽早初始化日志，覆盖风格初始化、配置/容器构造、退出刷写；启动前和强杀故障仍依赖 journal |

审计所有 `except`、返回 None/False 的外部调用失败分支和“只打印异常类型”的日志。人物路由当前存在异常后直接降级却没有日志的分支，也要补齐。明确的正常校验/跳过不制造故障。

不通过字符串猜测把多个日志合并成“一个问题”。本期展示真实日志记录；同一故障可能有底层原因和上层影响两条记录，用关联编号查看，不把日志条数称为故障次数。

## 5. 关键正常日志也要覆盖

| 链路 | 必须保留的事件 | 控制噪声 |
| --- | --- | --- |
| 启停 | 版本、boot ID、启动就绪、退出、风格初始化结果 | 每次启停记录，不输出环境变量 |
| 入站 | 认证后的消息接收时间、event/message ID、消息类型、direct/observer 去向 | 不记录正文；拒绝/忽略理由简短且可限频 |
| 回复排队 | 入队、批次开始、会话锁等待/防抖耗时、批次 message IDs | 防抖多消息必须可对应，不能仅留最后一条 |
| 模型 | 调用用途、开始/结束、耗时、provider/model、finish reason、token、安全拦截及解析结果 | 不保存 prompt 或模型正文；不复制 SDK 全量 DEBUG |
| 发送 | 开始、平台接受结果、可获得的 message ID、本地记录完成及总耗时 | 平台接受不等于用户已读；结果未知不自动重发 |
| 旁听 | 每批落库数量、会话、耗时、失败重缓冲 | 不为每个缓存步骤记一条 |
| 记忆整理/压缩/向量 | 有实际工作的任务开始/结束、处理数量/水位、耗时和失败 | 无新消息、无待处理向量不反复刷 INFO |
| 主动参与 | 实际评估结果、发送或跳过的标准 reason | 无活跃会话的定时轮询只保留内存心跳 |
| GM 写操作 | 操作名称、目标会话、开始/结束、成功/失败及关联编号 | 不记录发送内容、图片或口令；读接口不逐次持久化 |

现有 Gemini 诊断继续使用并补充上下文；OpenAI-compatible 路径补齐对应字段。模型用途至少区分 reply、identity_resolve、participation、consolidation、compression、embedding、caption、meme_review、dream_image。

关键上下文通过轻量 ContextVar 传递，后台任务入口明确继承或建立，结束时清理，验证并发会话不串号。使用 request/operation ID 做关联即可；本期不实现独立 trace/span 存储系统。

日志级别明确配置为能收集选中的 INFO。避免把全部 Uvicorn access、健康探测、GM 自动刷新和第三方 DEBUG 镜像到应用文件；它们会消耗空间而不能解释核心业务过程。

## 6. 后台如何看到问题

在现有工作台增加独立的“运行日志”入口，无会话也能打开；保留现有配色和组件，不重做管理界面。

- 顶部：当前版本、采集是否正常、日志实际占用/预算、队列与丢弃计数、最近写入时间。显示当前采样时间；没有数据不解释为系统健康。
- 列表：按新到旧显示时间、级别、模块/操作、会话/消息编号、安全摘要；可切换“错误与警告 / 关键过程”，按会话与关联编号筛选。
- 展开：具体原因、异常链、安全堆栈、上游状态/错误码/request ID、耗时及是否截断。
- 分页：游标读取，每页 50 条；受扫描上限限制时允许继续扫描，明确“尚未扫描完”或“记录已轮转”。筛选在扫描范围内进行，不声称搜索了全部历史。
- 刷新：进入时读取，提供手动刷新；仅该页可见时至多每 30 秒刷新第一页，隐藏/退出即停止，避免每 15 秒全量读日志。

API 复用 GM 鉴权和 no-store；列表返回安全摘要，详情同样脱敏。前端只当文本渲染，阻止日志内容变成 HTML。浏览器显示查询失败，不能渲染成“暂无错误”。

本期不做问题工单、已解决状态、全文搜索索引、趋势数据库、自动重试或告警群机器人。前端 API 失败显示服务返回的 error ID；浏览器全局错误回传后续有明确需求再做，不影响本次服务端主要故障覆盖。

## 7. 隐私与采集可靠性

禁止收集聊天正文、模型输入/输出、图片、请求体、Authorization、GM_TOKEN、API Key、飞书 token、Cookie、完整配置及 URL query。异常消息和上游 error.message 也要做长度限制、凭据和内容字段脱敏，不能认为它们天然安全。

保存代码文件/函数/行号，不抓局部变量，不保存异常对象。白名单提取上游元数据，禁止序列化 SDK 的 request/response/body。合成测试必须注入假密钥、私有正文和恶意 HTML，检查文件、journal 输出通道、API 和页面。

发生写入失败时，聊天继续工作，后台内存状态提示“采集异常/记录可能不完整”，并保留限频 stderr 诊断。采集模块自己的错误不能无限递归上报。查询不调用真实模型、不向飞书发消息、不扫描业务全文。

单机日志不能保证磁盘满、OOM、断电或主机失联时零丢失；轮转到期也会失去旧记录。应用页面宕机时继续依赖 journal/进程外检查，不能承诺后台始终可用。

## 8. 实施和验收顺序

1. 日志模块：固定容量文件、队列、脱敏、上下文与采集状态；先验证磁盘边界和异常原因保留。
2. 错误审计：逐项修复所有主要失败分支的原因缺失，包括隐式降级和后台任务；不改变聊天/发送重试行为。
3. 关键正常日志：补齐接收、排队、模型、发送、整理与 GM 写操作，确认默认 INFO 实际进入文件。
4. 后台页与 API：完成全局入口、列表/展开/过滤/游标和可见时刷新。
5. 离线验收：针对性测试完成后运行项目完整 unittest、ruff、diff 检查，以及 fake 工作台浏览器冒烟。
6. 交付代码后，按单独部署授权发布；核对日志在发布目录之外，生产仅做资源/日志元数据验收，不拿真实聊天当测试。
7. 独立评估系统 journal 上限。没有明确授权不修改系统设置、不 vacuum、不清理旧发布。

必要的针对性验收：

- 模型限流/超时/鉴权/JSON 截断，飞书非 JSON/权限不足/发送超时，数据库失败和各后台任务异常都有具体原因，而非只有异常类型。
- 正常回复、兜底回复、正常不发言、发送明确失败/结果未知可区分；一条接收消息能找到排队、模型和发送记录，多消息合并不丢关联。
- 并发会话与后台任务上下文隔离；正常取消不报错；启动/关闭能及时启用与释放 handler/线程，不重复挂载。
- 超大异常、连续写入和轮转后，应用日志始终在配置预算内；读取旧游标失效有清晰提示。
- 模拟日志目录不可写、磁盘写失败、队列满和查询过载，主业务不被日志阻塞；丢失/失败计数准确。
- 鉴权、no-store、脱敏、HTML 注入、分页与筛选覆盖范围通过；错误原因和代码位置能在页面看到。
- 测试进程空闲/持续写入/查询/错误风暴的内存与延迟增量；队列确实有界，扫描不会一次读入整个日志集。目标新增常驻内存不超过 10 MiB，超出需解释并压缩实现。

上线后在相似负载下对比服务 RSS、memory.current、PSI、swap-in/out、CPU 与每天日志字节数。以实际增长修订 32–128 MiB 范围内的容量；一次快照和 fake 测试不能替代生产稳定性验收。

## 9. 剩余边界

当前方案改善诊断，不修复 webhook 去重与异步处理之间的崩溃窗口，也不能让外部发送与本地落库原子提交。旧日志缺失的消息关联无法补齐。已有内存压力的根因尚未调查，本次不通过新增 swap、修改服务内存限制或关闭其他服务处理。
